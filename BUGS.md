# Bug Tracker

Quick-reference log of real bugs found in this project — check here
first before re-investigating something that might already be known.
Each entry links to [DEVLOG.md](DEVLOG.md) for the full root-cause
writeup and evidence; this file is deliberately terse, just enough to
recognize "have we seen this symptom before."

## Fixed

| Date | Component | Symptom | Fix | Verified |
|---|---|---|---|---|
| 2026-09-19 | Launcher (Windows) | Install button fails: `Failed to run npm install: program not found` | `Command::new("npm")` can't spawn a `.cmd` batch file on Windows; now invokes npm's own JS CLI entry directly through `node.exe`, same pattern as the `tsx` server spawn. [`885b724`](https://github.com/EmberCatz/OpenMarket/commit/885b724) — shipped in **v1.0.1**. | Real isolated `Command::new("npm")` spawn test reproducing the exact failure, then the fix, on a real Windows machine — not just a compile check. |
| 2026-09-19 | Repo structure / scripts | A diagnostic probe script (e.g. `Market Inventory Flake Probe.pluto`) shows up and gets run instead of/alongside `Market Sync.pluto` | User had copied the whole `scripts/` folder instead of just `Market Sync.pluto`, putting every dev-only probe on equal footing in OpenWF's script-runner UI. Probes moved to `scripts/probes/` so a whole-folder copy no longer sweeps them in. [`45b142f`](https://github.com/EmberCatz/OpenMarket/commit/45b142f) — repo-only change, **no launcher release needed**. | Traced directly from a real user's script_log output showing the probe's own diagnostic prints. |
| 2026-09-18 | Pricing | A relic's exact refinement (e.g. Radiant) shows "no price" instead of falling back like Mods/Arcanes do | Relics had no ladder-interpolation fallback at all, unlike mod/arcane rank. Both now share one `interpolateLadder()` function. | Verified via curl after a clean restart across multiple relics. |
| 2026-09-18 | Classification | Peculiar mods (Growth/Bloom/Audience/End) appear under the Arcanes tab, not Mods | They carry both `"mod"` and `"arcane_enhancement"` tags on warframe.market (the only items with that overlap); classification checked `arcane_enhancement` first. Reordered so `mod` wins the ambiguous case. | Confirmed by downloading the full catalog and checking the tag overlap directly, not guessed. |
| 2026-09-17 | Classification / safety | "Veiled Riven Mod" placeholders appear in the shop and are sellable | Riven filter checked for the exact tag `"riven"` instead of any tag *containing* `"riven"` — real veiled-riven placeholders are tagged `"riven_mod"`/`"veiled_riven"`. Selling one would have decremented the same stack a player's real earned Rivens live in. Fixed to a substring check. | Verified via curl: catalog count dropped by exactly 7 (one per weapon category) after the fix, nothing else changed. |
| (early dev, pre-release) | Backend / SpaceNinjaServer integration | `/api/sell.php` returns an opaque empty `HTTP 500` | That endpoint expects a raw string body (`Content-Type: text/plain`) and does `JSON.parse(String(req.body))` itself — sending `application/json` (the pattern used everywhere else) lets Express pre-parse the body first, breaking the call. Content-Type fixed to `text/plain` for this one call. | Confirmed by re-reading SpaceNinjaServer's own WebUI source, which uses the same header for the same endpoint. |

| 2026-09-18 | Launcher (all platforms) | Clicking "Open README" (Help tab) shows `Command plugin:opener\|open_path not allowed by ACL` instead of opening the file | `opener:default` in `capabilities/default.json` only grants the plugin's `open_url` command; `openPath()` (used for the local README button) needs its own `opener:allow-open-path` permission, which was never added. Fixed by adding that permission. Requires a new build — capability ACLs are compiled into the binary, so this is broken on every release through **v1.0.1**. | Permission identifier confirmed against the local Tauri-generated `gen/schemas/windows-schema.json` (not guessed); UI fix not yet build-tested end-to-end. |
| 2026-09-20 | Launcher install (Homebrew/Linuxbrew) | Install fails: `Could not find npm's CLI entry point relative to /home/linuxbrew/.linuxbrew/Cellar/node/<ver>/bin/node` | The v1.0.1 npm-spawn fix (see the entry above) was applied to **all** platforms, but the underlying `.cmd`-can't-spawn problem is Windows-only — Unix's `Command::new("npm")` already worked fine there. On Homebrew, npm lives at `<brew prefix>/lib/node_modules/npm/bin/npm-cli.js`, with no fixed relative path to node's own (Cellar-versioned) directory, so the guessed Unix fallback path never matched. Manual `npm-cli.js` resolution is now Windows-only (`#[cfg(target_os = "windows")]`); Unix spawns `npm` directly via `$PATH`, same as it already does for `node`. | Windows branch re-verified with a real `cargo check`. Unix branch **not** compiled here (no Linux Rust target on this machine) — verified by reasoning only, same shape as the already-working `check_node`. Needs a real Linux test before/soon after release. |
| 2026-09-20 | Pricing | Newly-added items (e.g. the weapon Prime parts/sets added the same day) show no price at all, could stay that way up to a week | The weekly price sweep is purely time-gated (`lastRefreshCompletedAt` + 7 days) — a real, non-stale sweep from before a catalog change means it won't re-run, so a brand-new slug just has no entry until the next natural weekly boundary. Added an hourly backfill pass (`runBackfillSweep()`) that diffs the current catalog's slugs against what's already priced and sweeps only what's missing, independent of the weekly timer. Also added a manual "Update Prices" button (`POST /api/refresh-prices`) for a user who wants a full resweep right now instead of waiting on either. | Verified via scratch-port curl: server startup found 377 missing weapon-Prime slugs and backfilled all of them in the background without touching `lastRefreshCompletedAt`; confirmed real prices (Boltor Prime Barrel 10p, Akmagnus Prime Set 30p) afterward. Manual endpoint verified to return 409 while a sweep is already running, 202 otherwise. UI verified in a real browser (Playwright) — button shows "Updating Prices…" disabled during a sweep, including on page load if one was already in progress. |
| 2026-09-20 | Launcher (Linux) | Closing the launcher (taskbar/dock "Quit", session logout, `kill`, Ctrl+C in a launching terminal) without first clicking Stop leaves the supervised Node server running as an orphan, still bound to the port — the next launch (including right after an auto-update) then fails to start it | The existing `CloseRequested` window-event cleanup only fires for a graceful window close (the X button, Alt+F4). Those other paths deliver SIGTERM/SIGINT directly to the process, which neither Rust nor Tauri handles by default, so the process just dies without running any cleanup. Added a `tokio::signal::unix` handler (SIGTERM + SIGINT) that kills the supervised child before the launcher itself exits — Unix-only via `#[cfg(unix)]`, doesn't touch the already-working Windows path. Deliberately does **not** use `PR_SET_PDEATHSIG` (the more bulletproof "kill my child no matter how I die" mechanism) — its semantics track the specific OS thread that forked the child, not the process, which is a real footgun on a multi-threaded tokio runtime (the tracked thread could get recycled by tokio's own thread pool mid-session, killing the server for no visible reason). | Reported by a real Linux tester. Windows re-verified with `cargo check` (the new code is fully `#[cfg(unix)]`-gated, so it's compiled out and inert there). **Unix branch not compiled or run here** (no Linux Rust target on this machine) — a plain `tokio::signal` handler has no known platform gotchas, but this genuinely needs a real Linux smoke test (send SIGTERM to a running launcher, confirm the server process is actually gone) before/soon after it ships. |

| 2026-09-23 | Backend | `POST /internal/inventory-snapshot` (or any large `/api`/`/internal` body) fails with `PayloadTooLargeError: request entity too large` | `express.json()` was mounted with no explicit `limit`, so it used Express's built-in 100kb default — too small for a full inventory snapshot once Mods+Arcanes+Relics+Prime parts/sets were all added. Set `limit: "10mb"` on the `express.json()` call. | Scratch-port curl with a 200KB test body: returned `413` before the fix, `400` (route-level shape validation, as expected for a bogus payload) after. |

| 2026-09-25 | Backend | `GET /api/items` (and therefore the whole shop) 502s with no internet connection, even with a fully populated cache from before | The item catalog had zero disk persistence — pure in-memory, re-fetched live on every access after 1 hour, so a failed live fetch left literally nothing to serve. Gave the item catalog `server/items-cache.json` disk persistence + a committed `items-cache.seed.json`, mirroring the pricing cache's already-working shape; the automatic hourly re-fetch was also removed entirely (catalog now only refreshes via "Update Data"). See [DEVLOG.md](DEVLOG.md#offline--local-data-model). | Verified live: deleted the disk cache and seed, confirmed `/api/items` returns `[]` (not a 502) and the frontend shows a clear "connect and click Update Data" message instead of the old opaque error; restored and confirmed normal operation. |
| 2026-09-25 | Icons | Every item shows a broken image icon | Icons were hotlinked directly to `https://warframe.market/static/assets/...`, a live network dependency that had also broken outright (warframe.market apparently changed something on their end) - reported via Discord. Replaced entirely with local, offline icon extraction from a real Warframe client install via Warframe-Exporter - see [DEVLOG.md](DEVLOG.md#offline--local-data-model) for the full design, the folder-recursion gotcha that made a naive version impractically slow, and why the extraction tool itself isn't bundled in this repo. | Verified live on Windows via a real extraction run + Playwright screenshots: Prime Warframe/weapon sets, Arcanes, most Relics/Mods render real art. **Linux path unverified on real hardware** - see "Known / open" below. |
| 2026-09-25 | Icons | ~800 relics never got their real icon, even after a successful local extraction | `ExportRelics.json` has no bare/unrefined entry for any relic - every relic is 4 separate refinement-suffixed keys (`Bronze`/`Silver`/`Gold`/`Platinum`), each pointing to a different generic per-quality icon shape, not unique art. The generator was looking for a bare key that never exists. Fixed by resolving via the `Bronze` (== this app's default `intact` refinement) entry instead. | Relic icon coverage went from ~0% to 96.6% (799 relics) on a real extraction run; the remaining ~3% are items too new for the local Public Export snapshot to have at all, not a code gap. |

## Known / open — not fixed yet

| Found | Component | Symptom | Status |
|---|---|---|---|
| 2026-09-24 | Launcher (Linux, Steam Deck) | AppImage window opens (correct title bar, correct size) but the webview content is entirely blank/gray, or fails outright with `Could not create default EGL display: EGL_BAD_PARAMETER`. Node.js confirmed installed and working. | **Root cause confirmed. A build-pipeline fix exists (`.github/workflows/release.yml`'s `fix-linux-appimage` job, added 2026-09-24) but has never actually run in real CI or been tested on real hardware** - see `internal/patch-notes/unreleased.md` for the fix's own details and its explicit "verify via `workflow_dispatch` against a real Steam Deck before trusting this" recommendation. Root cause: the AppImage bundles its own `libwayland-client.so.0`/`libwayland-cursor.so.0`/`libwayland-server.so.0`, which conflict with SteamOS's own Mesa/EGL stack. Confirmed-working manual fix in the meantime: extract the AppImage, remove those 3 libs, launch `./AppRun` directly. **Don't cut a tagged release with real-user auto-update impact until this has been verified on real Steam Deck hardware** - see the next row for a second, independent Linux-verification gap that landed the same week. |
| 2026-09-25 | Icons (Linux) | Local icon extraction (see DEVLOG.md's "Offline / local data model") ships a `Warframe-Exporter-CLI.AppImage` for Linux, defensively `chmod`'d and run with `APPIMAGE_EXTRACT_AND_RUN=1` in case FUSE isn't available - **none of this has been run on real Linux/Steam Deck hardware**, only reasoned through (this dev environment is Windows-only). | **Not a crash risk either way** - if something's wrong here, the existing graceful placeholder-icon fallback just keeps showing placeholders, same as before this feature existed. Still, don't present Steam Deck icon support as "confirmed working" (or bundle it into a real release) until someone actually runs it there - ideally in the same verification pass as the row above, since both are blocked on the same missing resource (real Steam Deck access). |
| 2026-09-19 | Frontend order flow | Buy/Sell disables both buttons on click, but there's **no timeout** — if `Market Sync.pluto` never picks up the order (usually because it's not actually connected), the buttons stay disabled forever with zero error shown. A page reload/re-render resets the disabled state, so repeated clicks can queue multiple real duplicate orders for the same item. Confirmed via two independent real user reports (4x and 2x duplicate orders), both traced back to the script not being connected — not a queueing bug itself, but the missing timeout is what let it go unnoticed. | **Not fixed** — proposed: a timeout that surfaces a real error after ~30s, plus a guard against queueing a second order for an item that already has one pending. |
| 2026-09-19 | Pluto script / launcher | `Market Sync.pluto` has the backend port (`7890`) hardcoded. If the launcher's configured **Server port** is ever changed away from `7890`, the script keeps polling the old port forever — no error on either side, just permanently stuck on "Waiting." | **Not fixed** — not urgent (requires the user to have changed the default), but a real footgun with no diagnostic surfaced anywhere. Documented in the Discord thread checklist as a manual thing to check. |
